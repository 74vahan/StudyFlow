# Ручные тест-сценарии — StudyFlow

Документ для экзамена: ручная проверка основных потоков приложения.
Каждый сценарий привязан к acceptance-критерию (AC-xx) из `requirements.md`.

## Подготовка окружения

1. Поднять БД и приложение (из `StudyFlow_infra/`):
   ```bash
   docker compose up -d
   ```
   либо локальный MySQL + `npm run dev` из корня (нужны `DATABASE_URL`,
   `AUTH_SECRET`, `TEACHER_PIN_HASH_B64` в `StudyFlow_image/.env.local`).
2. Открыть http://localhost:3000.

**Тестовые данные (dev):**

| Роль | Доступ | Состояние |
|---|---|---|
| Учитель | PIN `123456` | — |
| Ученик Alice | `alice@test.com` / `alice123` | в классе, есть задача |
| Ученик Bob | `bob@test.com` / `bob12345` | не в классе (pending) |

> Перед прогоном изоляции (TS-07) убедиться, что у Alice есть задача, а Bob
> не состоит в классе. При необходимости — создать заново через учителя.

## TS-01 — Регистрация ученика (AC-01)

**Цель:** новый ученик может создать аккаунт; понятные ошибки на невалидный ввод.

| Шаг | Действие | Ожидание |
|---|---|---|
| 1 | Открыть `/register` | Форма email + пароль |
| 2 | Отправить пустую форму | Ошибки валидации полей, запрос не уходит |
| 3 | Ввести слабый/короткий пароль | Понятная ошибка, регистрация отклонена |
| 4 | Ввести `new@test.com` + валидный пароль | Успех: сессия создана, редирект (в класс или `/pending`) |
| 5 | Повторно зарегистрировать тот же email | Ошибка «email занят» (HTTP 409), без дубля в БД |

## TS-03 — Вход учителя по PIN + блокировка (AC-01)

| Шаг | Действие | Ожидание |
|---|---|---|
| 1 | С лендинга «Log in as teacher» → `/teacher/login` | Поле 6-значного PIN |
| 2 | Ввести неверный PIN | HTTP 401, понятная ошибка |
| 3 | Повторять неверный PIN до лимита | Срабатывает lockout: HTTP 429, временная блокировка |

## TS-07 — Изоляция данных (AC-04) ⭐ главный критерий

**Цель:** ученик не видит и не может менять чужие задачи. Проверка двумя аккаунтами.

| Шаг | Действие | Ожидание |
|---|---|---|
| 1 | Учителем назначить задачу «Задача Alice» только Alice | Создана для Alice |
| 2 | Войти как Alice | В списке — её задача |
| 3 | Войти как Bob (предварительно добавлен в класс, но без этой задачи) | Задачи Alice НЕ видно |
| 4 | Будучи Bob, запросить `GET /api/tasks/<id_задачи_Alice>` напрямую | HTTP 404 (сервер фильтрует по `assignee_id` из сессии) |
| 5 | Будучи Bob, `PATCH` статус задачи Alice напрямую | Отклонено, чужая задача не меняется |

> Изоляция на сервере: `WHERE assignee_id = session.userId`
> (`src/lib/tasks/mysql-store.ts`), клиент `assignee_id` не передаёт.

### Как проверялось

- UI-поток в браузере: вход учителя по PIN (верно/неверно), панель учителя,
  создание/назначение задачи, лендинг, `/pending` со Змейкой, dashboard,
  список задач, поиск/фильтр, смена статуса учеником, переключение en/ru/hy,
  выход.
- Изоляция и права (TS-07/08/09) — прямыми запросами к API под реальной
  сессией (cookie) каждой роли:
  - Ученик Bob: `GET /api/tasks` → `{tasks:[]}`; чужая задача `GET`/`PATCH`
    → 404; `POST` → 403; `DELETE` → 403.
  - Учитель: полный `PATCH` задачи → 200; `DELETE` → 200.
- Сохранение (TS-12) — смена статуса подтверждена в MySQL и пережила refresh.
- Мобильный экран (TS-13) — проверка отсутствия горизонтальной прокрутки
  (`scrollWidth === clientWidth` при 375px) на логине и панели учителя.

### Вне объёма

- **AC-07 (AI-помощник)** — фича не реализуется (решение по проекту).
- **AC-10 (прод-деплой)** — проверяется отдельно после публикации в GCP.
